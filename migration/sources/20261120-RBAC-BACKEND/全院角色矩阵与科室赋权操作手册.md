## 三、管理工具 superset_rbac_manage.py

部署位置：服务器 `/home/superset/superset_home/scripts/`（与 rbac_policy.json 同目录）；本地存档 `offline-bundle/scripts/`。

环境变量（凭据一律外部注入，严禁写进脚本）：

```bash
export SUP_BASE=http://superset-web:8088      # 容器内；宿主调试用 http://127.0.0.1:8180
export SUP_ADMIN=admin
export SUP_ADMIN_PWD=$(cat /home/superset/secrets/ADMIN_INIT_PASSWORD)
export PGPASSWORD=$(grep -E '^POSTGRES_PASSWORD=' /home/superset/.env | head -1 | cut -d= -f2-)
```

运行方式（worker 容器内）：

```bash
cd /home/superset && docker exec -e PGPASSWORD="$PGPW" -e SUP_BASE=http://superset-web:8088 \
  -e SUP_ADMIN=admin -e SUP_ADMIN_PWD="$ADMPW" -e PYTHONIOENCODING=utf-8 \
  superset-worker /app/.venv/bin/python /app/superset_home/scripts/superset_rbac_manage.py <子命令>
```

七个子命令：

| 子命令 | 作用 | 示例 |
|---|---|---|
| `status` | 总览计数+受保护绑定核查 → /tmp/rbac_status.json | `... manage.py status` |
| `audit` | 全量赋权审计（角色→成员、用户→角色）→ /tmp/rbac_audit.json | `... manage.py audit` |
| `grant-user` | 给单个用户加角色 | `... manage.py grant-user --username 003158 --role 报表授权_护理部管理` |
| `revoke-user` | 给单个用户摘角色 | `... manage.py revoke-user --username 003158 --role 报表授权_护理部管理` |
| `grant-dept` | 给科室角色全员加角色 | `... manage.py grant-dept --dept-code 0104 --role 报表授权_护理部管理` |
| `revoke-dept` | 给科室角色全员摘角色 | `... manage.py revoke-dept --dept-code 0104 --role 报表授权_护理部管理` |
| `sync-policy` | 按 rbac_policy.json 补齐（missing 补、extra 只报告） | `... manage.py sync-policy --dry-run` → 确认后 `--apply` |

所有 grant/revoke 支持并默认建议先加 `--dry-run` 预览。写后自动 DB 回读断言，失败即报错不静默。

## 四、红线（违反会造成生产事故）

1. **受保护绑定**：`001283 ↔ 报表授权_病案离院明细`、`001643 ↔ 报表授权_抗菌办` 为人工冻结专项。任何工具与人工操作都不得摘除；revoke 命中会被自动拒绝（`refused_protected`）。
2. **前缀校验**：本工具只接受 `报表授权_` 前缀目标角色，防止误操作 Gamma/科室_/role_ 通道。
3. **同步窗口**：每日 06:00 用户同步、06:15 warmup。赋权操作避开 06:00–06:20；工具写操作会持有 `/tmp/user_sync.lock`，与同步互斥等待（最长 120 秒）。
4. **严禁 `superset init`**；严禁改动数据集 SQL 与统计口径；角色定义/看板绑定/数据集授权的变更只走 `apply_rbac_matrix.py` / `rollback_rbac_matrix.py`，人员赋权只走本工具。
5. **调岗风险（重要）**：每日用户同步只回收 `科室_`/`role_` 角色成员；人员调岗/离职时其 `报表授权_` 角色**不会**自动回收，需人工执行 `revoke-user`（或整科室 `revoke-dept`）。建议每次人事变动通知后先跑 `audit` 核对。
6. `sync-policy` 的 extra 条目（用户持有 policy 之外的其他 报表授权_ 角色）只报告不回收——审慎原则；需要回收时人工评估后单独 `revoke-user`。

## 五、排障速查

| 现象 | 处置 |
|---|---|
| `FATAL: 拒绝grant...前缀` | 角色名没写 `报表授权_` 前缀；确认角色名后重试 |
| `用户不存在：003158` | 工号核对；用户由每日同步维护，新员工等次日 06:00 后再试 |
| `科室角色不存在` | 科室角色格式为 `科室_<名称>（<6位码>）`（全角括号）；跑 `psql -c "SELECT id,name FROM ab_role WHERE name LIKE '科室_%'"` 核对实际名称 |
| 登录失败 / 401 | `SUP_ADMIN_PWD` 未注入或密码变更；从 `/home/superset/secrets/ADMIN_INIT_PASSWORD` 重取 |
| 获取锁超时 | 06:00 同步或 warmup 正在运行；稍后重试，勿强行删锁文件 |
| PUT 后回读断言失败 | 工具自动中止并报错；跑 `audit` 核实现场，必要时按本手册矩阵手工恢复 |
| 导出 403（非 Admin） | 正常收紧行为；如属授权用户，核对是否挂了对应 报表授权_ 角色 |
