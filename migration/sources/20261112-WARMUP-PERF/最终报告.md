### 教训与批内修复（重要）
首版 g5 的 render() 在每次 MutationObserver 回调里都执行 softTip()（含两次 React fiber 深遍历）并常驻创建 `#hdt-span-tip` 节点；59 号页 antd 下拉/虚拟列表交互产生高频变更批，**主线程被 render 饿死（页面冻结 60s+，两次复现）**。修复：observer 节流 250ms + 软提示节点"有内容才创建、空即移除"。修复后全部场景通过且交互流畅。同版本号 20261112g5 内完成替换（缺陷版在线约 35 分钟，仅本批测试流量接触）；`/custom/` 资源 no-cache 强制重校验，用户端不会残留缺陷版。

## 任务 2：每日清晨缓存自动预热引擎

### Cache Key 100% 命中的实现原理
1. **模板抄录**：用 CDP 在真实 Chrome 首屏逐条抄录 10 个目标看板（72/73/74/32/35/41/45/46/60/63）浏览器实际发出的 `/api/v1/chart/data` 请求 **39 条**（29 个图表 + 10 个 filter_time 附加查询），存为 `warmup_templates.json`。关键发现：看板图表请求 URL 携带 `?form_data=%7B%22slice_id%22…%7D&dashboard_id=N` 查询串且**参与服务端 get_form_data 合并**——URL 与请求体必须原样重放。
2. **每日重放**：`superset_cache_warmup.py` 以管理员会话（JWT+CSRF，凭据由 run_warmup.sh 从 `/home/superset/.env` 的 `ADMIN_INIT_PASSWORD` 注入容器环境，脚本零硬编码）**串行**重放全部模板：间隔 2s、单请求超时 90s、仅把 `force` 改为 `true`——源码级核实 `force` 不参与缓存键，只跳过旧缓存读并重写新值+重置 TTL，从而既刷新数据又保证浏览器次日 force=false 打开必然命中。
3. **缓存键与用户无关**（生产 RLS=0；10 个目标数据集 SQL 无 `current_user_id()`——均已核实），管理员预热全院共享。
4. **保护门禁**：文件锁 `/tmp/superset_warmup.lock`（flock 防重入）；连续 3 个请求失败自动熔断中止当日预热（绝不拖累 HIS/ODS 源库）；结构化 `SUMMARY json=…` 日志行（总数/成功/耗时/熔断）。
5. **调度**：宿主机 cron `15 6 * * * /bin/bash /home/superset/superset_home/scripts/run_warmup.sh >> /home/superset/logs/warmup.log 2>&1`（错开 02:00 备份与 06:00 用户同步）。

### 真实验证数据
- 3 次真实运行（16:42 首跑 / 17:31 cron 同命令复跑 + 手动 no-force 验证轮）：**39/39 ok，228~231s**，63 号两个 46.3s/45.0s 慢查询全部强制刷新成功，零熔断。
- Redis db1 实测：键 `flask_cache_<cache_key>` 与预热日志逐条对应，**ttl=86240s≈86400**（响应体 `cache_timeout:86400` 双重实证，DATA_CACHE_CONFIG 未设 timeout 时继承全局 CACHE_DEFAULT_TIMEOUT=1 天——源码级核实）。
- no-force 验证轮：39/39 全部 120~700ms 命中（63 号 46.3s→142ms）。
- **浏览器终验**（Chrome156 + Chromium87 打开 72/73/74/32/45/63）：**31/31 个 chart/data 响应 `is_cached:true`**，详见测速表。

## 偏差与教训（如实登记）

1. g5 首版 render 风暴冻结（见任务 1）——第三方脚本在 React 管理容器内高频读写必须节流+按需建节点。
2. Superset 6.1 看板图表请求逐图表 POST 且 URL 带 form_data 查询串；另有 filter_time 附加查询——预热模板必须 URL+体原样重放，"只跑裸 SQL"或漏查询串都会 Miss。
3. 冷响应不含 `is_cached:false` 字段（字段仅在命中时出现 true）——命中判定按 `is_cached===true`，勿以缺省当 false 之外的语义。
4. 59 号筛选条自身会在页面加载/搜索时发 4~6 个 chart/data 内务请求（filter_select 选项 ds361、filter_time 预览 ds359、图表空查询）——守卫"不发慢查询"的断言应排除这些内务请求，按 viz_type/slice_id 区分。
5. 39 号此前 sweep"表格未出"按本批实测为 16~18s 慢载（默认 7 天窗），无超时缺陷；保留橙色引导即可。
6. 63 号冷查询 43~65s 随源库负载波动，>60s 时前端报"查询失败"——预热是当前架构下唯一稳妥解（Oracle 11g 源库不可加索引）。
