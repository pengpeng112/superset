## 一、结论

**基础部署有实证，自动迁移完成了大量对象创建，但尚不能认定报表业务迁移完成或统计结果准确。方案 A 原样执行不推荐。**

原 SQL 的提取资产值得保留：对生产 212 个 SRD 数据集逐一解析，包装内层查询全部与“提取 SQL 经原脚本 NULL 替换后”的语法树一致。这证明目前内层查询能追溯到提取资产；**不证明参数替换正确，不证明提取结果与老系统运行时逻辑完整一致，也不证明报表数字一致**。

推荐沿用这些资产，恢复原参数与计算口径，修复看板关联，逐数据集设计权限和负载控制，再分批验收。无需更换 BI 产品或从头重做。

### 3.1 重复对象与失败账目的具体依据

| 源对象序号 | 模块 / 数据窗口 | 首批图表 / 数据集 | 重试图表 / 数据集 |

两份对象的内层查询都对应同一条源 SQL，重试并未增加源对象覆盖。重试脚本以裸 `dw` 名命中失败对象，缺少模块维度；名称去重也未可靠实现完整分页，不能用图表标题作为唯一键。

正确账目是：**339 = 209 已覆盖源对象 + 130 未覆盖源对象；212 = 209 首批对象 + 3 重复重试对象；130 = 86 原 SQL 失败记录 + 44 其他未覆盖对象。**

首批日志有 `BATCH_DONE 209 of 339`，之后出现 `PermissionError`；脚本本应写入的 `deploy_srd_result.json` 现不存在。因此 44 个对象的具体 API 失败原因无法从完整首批结果文件恢复，不能在缺少证据时直接定性。应补记“结果未完整保存”，逐项做结构核查和受控重试。

### 3.2 看板并非只差 3 张图表

仪表板 3–19（核心、源库两批、SRD）共 17 个，布局引用了图表，但 `dashboard_slices` 关联均为 0；只有病案两个仪表板的布局与关联一致。SRD 的 13 个看板均没有原生筛选器。

迁移脚本只写 `position_json`，布局中还缺少 `ROOT_ID` 节点，需一并按正常编辑器生成的结构修正。官方 6.1.0 模型用图表关系提供 slices 与数据集信息；仅创建布局 JSON 不足以完成关联。[Superset 6.1.0 仪表板模型](https://github.com/apache/superset/blob/6.1.0/superset/models/dashboard.py)

这里认定的是元数据缺陷；本轮没有浏览器逐盘渲染验收，不把它扩写成“已实测所有看板都打不开”。

### 3.3 报表计算层尚未完整迁移

覆盖的 209 个不同源对象中，**138 个 SRD 原文包含 `compute(...)` 控件**。当前脚本只迁移 SQL 返回列并建立 raw 表格，没有迁移这些控件表达式。例如欠费明细原文含 `sum(total_amount for all)`、`sum(repay_amount for all)` 等合计表达式。

这些控件可能是合计、比率、标签或格式，不能全部当缺失业务指标；但必须逐条分类。SQL 能执行，并不代表旧报表的合计、分组、百分比、交叉表或运行时过滤均已复现。[PowerBuilder 官方 DataWindow 表达式说明](https://docs.appeon.com/pb2022/datawindow_reference/XREF_53004_About_DataWindow.html)

原解析器还用最长表头文本推测标题，以位置重叠推测列头对应关系。查到一列 `DATETIME` 被命名为“预交金余额：”，说明已有明显列名错配，不能把提取标题与列头全部称为“原版准确映射”。

## 四、方案 A 是否可行

### 4.1 能改善的部分

如果某条旧报表的日期参数确实应改为可选过滤，且查询是简单明细、时间列输出完整、外层条件能可靠下推、权限及负载已验证，删除被错误 NULL 化的谓词后再配置筛选器，**可能成为该报表的实现选项**。

但当前没有满足上述条件的 131 条准确清单，也没有相应性能证据，不宜直接批量执行。

### 4.2 原建议存在五个问题

1. **“131 张”的范围尚未证实。** 本轮对生产 SQL 做 Oracle 语法树检查：212 个 SRD 对象中，161 个含直接 NULL 比较，涉及 159 个不同源对象。每个受影响对象至少有一个 WHERE 查询块可保守推导为不能得到 TRUE；其中 126 个对象的源查询顶层 WHERE 也不可满足。**这不是“161 张结果必定全空”**：无 GROUP BY 的聚合可能返回 0/NULL，嵌套子查询或 UNION 可能只损失部分结果。本轮未执行业务 SQL，不给实际空表数量下结论。
2. **参数不只有日期。** 已出现科室、患者标识、住院次、药品、库房、费别、统计层级、列选择等参数。把这些条件删除，会扩大人群、混合院区/科室/库房或改变指标口径。
3. **外层筛选能力有限。** `NULL` 普通比较在 Oracle 中为 UNKNOWN，WHERE 不保留 UNKNOWN。外层条件无法恢复内层丢失记录；先删日期后做全量 GROUP BY，如果日期未出现在输出中，后续外层筛选也无法重算指定时期汇总。205/212 个 SRD 数据集没有时间主列，仅 7 个数据集存在被元数据识别的时间列。[Oracle 11g NULL 语义](https://docs.oracle.com/html/E26088_01/sql_elements005.htm)
4. **“1000 行兜底不会拖垮库”不成立。** 当前 212 张均为 raw 表格、row_limit=1000；其中 111 张 SQL 含 GROUP BY、33 张含 ORDER BY、33 张含 UNION。限制最终输出不限制底层扫描、关联和聚合成本；一个返回一行的 SUM 仍可能处理全表。ROWNUM 可能帮助某些执行计划早停，但不能保证每条复杂查询早停。当前还有一个看板容纳 50 张图表的布局，打开时并发负载需单独评估。[Oracle 聚合与排序执行说明](https://docs.oracle.com/cd/B10500_01/server.920/a96533/opt_ops.htm)、[Oracle 11g ROWNUM](https://docs.oracle.com/cd/E11882_01/server.112/e41084/pseudocolumns009.htm)
5. **重建不是必要动作。** Superset 虚拟数据集是 SQL 定义，不会因“重建”自动生成数据仓库。优先按已有 ID/UUID 更新 SQL、列属性和图表参数，保持授权、看板、原生筛选目标等引用；新增对象应有稳定来源键和回滚依据。

`SQLLAB_TIMEOUT=120` 已配置，但这不能作为所有看板查询都已具备数据库级超时、取消及并发限额的证明；本轮未做超时取消实测。

### 4.3 建议替代：恢复参数，内层有界查询，再接看板筛选

按原 `pbd + dw`、源 SQL 哈希、参数定义恢复映射；来源存在同名版本时再加入内容哈希区分。不要用展示标题或易变化的清单序号作长期唯一键。

日期筛选应进入原本需要参数的内层 WHERE。Superset 6.1.0 官方支持 `get_time_filter()`，`remove_filter=True` 用于将处理过的时间条件从外层移除；也支持 `filter_values()` / `get_filters()` 处理其他筛选条件。[Superset 6.1.0 SQL 模板](https://superset.apache.org/admin-docs/6.1.0/configuration/sql-templating/)

以下只是日期部分的结构示例，**不能覆盖现有 SQL 整段直接运行**；原连接条件、状态/退费口径、科室权限和指标列均须保留：

```sql
{% set tf = get_time_filter(
    default="Last week", target_type="TIMESTAMP", remove_filter=True
) %}

SELECT /* 已核对的列与指标 */
FROM /* 已核对的原表与连接 */
WHERE /* 保留原业务及权限条件 */
{% if tf.from_expr and tf.to_expr %}
  AND P.DISCHARGE_DATE_TIME >= {{ tf.from_expr }}
  AND P.DISCHARGE_DATE_TIME <  {{ tf.to_expr }}
{% else %}
  AND 1 = 0
{% endif %}
```

此例不传 column，用于读取看板原生时间范围；落地时需在对应 Oracle 11g 连接上检查渲染出的时间表达式。默认有界时间可选近期 7 天；允许的最长区间建议先限 31 天，实际按报表与 DBA 核定。**此示例本身尚未实现最大区间校验**，实施时要在服务端/SQL 模板加入校验，拒绝或退回默认范围。清空筛选器不能退化为历史全量。

原 SQL 若按自然日用 `TRUNC(date)` 与含尾日比较，先核对边界再转为半开区间，确保尾日记录与旧口径一致；结存、在院快照、同期比较等报表不能机械改成统一的起止日期范围。

其他参数的字符串取值使用 `where_in` 等安全引用；用于选择字段/排序/统计级别的参数必须白名单。**科室筛选只是用户交互，不能代替强制权限过滤**。全院汇总、单科室汇总、患者明细应按不同授权范围设计。
