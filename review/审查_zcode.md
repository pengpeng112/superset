## A. 需求覆盖度自评（R1~R7）

| 需求 | 方案落点 | 自评 | 保留意见 |
|---|---|---|---|
| R1 开源+直连 Oracle/MySQL+AI 参与+功能丰富 | 论断 1/2/14；REST API（论断 3）承载 AI 参与 | 覆盖 | "功能丰富"依赖生态插件，Superset 图表类型不及商业 BI（如帆软的中国式报表/填报弱），若用户要"类 Excel 复杂报表"则是短板 |
| R2 无收费墙+导出 Excel | 论断 1（Apache 2.0）+论断 5（xlsx 导出） | 覆盖 | 无保留 |
| R3 外部 AI 经 API 建报表+人工 GUI | 论断 3（全套 REST API+YAML 导入导出）+Superset 原生 GUI | 覆盖 | "AI 建 chart 的 JSON 参数较复杂（vizType/params 结构）"，但 YAML 打包导入可降低复杂度；无广泛公开案例（风险 2 已列） |
| R4 百万行查询与导出 | 论断 6/7 + 轨道二 | 覆盖 | xlsx 硬上限 104 万行是格式限制非工具限制；百万行网页端浏览体验有限，已用"看聚合、导明细"双轨规避 |
| R5 角色+科室/人员行级隔离 | 论断 8/9/10（RLS+RBAC+AD 映射） | 覆盖 | RLS 需逐数据集配规则，30 科室×多数据集的规则维护量需模板化（Jinja 变量可部分解决） |
| R6 嵌入其他系统 | 论断 11/12（Guest Token+rls_rules） | 覆盖 | 宿主系统需写一个换 token 小接口（开发量小但非零） |
| R7 AI 本地修改 | ZCode CLI 本身即本地执行通道（调 Superset API、跑 Python 导出） | 覆盖 | 无保留——R7 由执行载体满足，不依赖 BI 特性 |

**自评结论**：R1~R7 全覆盖，最弱处在 R1 的"中国式复杂报表"维度与 R3 的"AI 建报表成熟度未经验证"。

## B. 自发问题（自查发现）

1. **中国式报表缺口**：Superset 强于看板/图表，弱于"单元格级复杂报表+套打"（HIS 财务/上报报表常见形态）。方案未明确此缺口的处置（接受/外挂工具/轨道二脚本弥补）。若科室要的是"类 Excel 网格报表"，Superset 的 Table 图表可做但样式能力有限。
2. **实时性未讨论**：HIS 数据经 ODS 同步，报表数据天然 T+1 或小时级；用户未提实时需求，但建议明确写出以免预期错位。
3. **元数据库选型**：Superset 自身元数据默认 SQLite，生产须换 PostgreSQL/MySQL——实施步骤未写明。
4. **升级维护**：Superset 大版本升级（2.x→3.x→4.x）有破坏性变更史，1~2 人团队需锁定版本策略。
5. **SuperSonic 的排除/观察定位**：其语义层（HeadlessBI）对医院"指标口径统一"价值高，若 Oracle 兼容实测通过，可能优于"Superset+人工维护口径"的组合——方案列为试点观察，但我认为应更主动：可作为并行试点而非仅备胎。
6. **论断 12 的包名**：@preset-sdk/embedded 是 Preset 公司的包（非 Apache 官方），开源版用户用它有轻微供应链顾虑（低风险，如实标注）。
7. **凭据治理**：GLM 在本地跑导出脚本时将接触 Oracle 凭据，凭据存放位置（环境变量/密钥文件）未在方案中约定。
