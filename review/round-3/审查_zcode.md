## 2. 自发发现的问题与风险（初审）

### 技术事实类
1. **`apache/superset:6.1.0` 镜像 tag 存在性未在线验证**：v2 调研确认 6.1.0 为当期正式版，官方镜像应有该 tag，但起草时未执行 docker pull 验证（离线介质制备 P2-S2 首次拉取才暴露）。缓解：P2-S0/S2 已设检查点；版本取"6.1.x 当期补丁版"留了弹性。
2. **Vastbase 驱动 `opengauss-sqlalchemy` 包名是候选而非定论**：已在 P2-S2 风险注记与 P4-S4 实测条款中标注"以实测为准"（对齐 v2 风险 1）。pymssql 对 SQL Server 新版（2019+）的加密连接（TLS）在内网环境可能需 `tds_version=7.3+` 参数——方案未展开，P4-S2 的 URI 模板偏简，**留审查方补充**。
3. **oracledb URI 写法**：`?service_name=orcl` 与 `?sid=orcl` 双写法已列；10.10.8.216 的 Oracle 服务名/SID 实际值未核实（起草时未获 SQL 执行授权，不做数据库登录验证）——P1-S6 由执行者验证。
4. **Playwright 离线安装的时序**：`playwright install --with-deps chromium` 在构建机（外网）执行正确；但 Playwright 浏览器版本与 playwright pip 包强绑定，升级镜像时需同步升——已在 P5-S3 标注升级耦合，但 **P2 的 Dockerfile 未写死 playwright 版本的锁定策略**（写的是 `<当期稳定版>` 占位），执行时应 pin 精确版本。
5. **中文字体与 Playwright 截图**：定时报告截图中文乱码风险（debian 基镜像无中文字体）——**方案未提及安装 fonts-noto-cjk**，这是 P2-S2 Dockerfile 的可能缺件，已列入"附：审查关注点"第 3 条。
6. **P1 本地外网可用性未设检查步骤**：P2-S0 有外网验证，但 P1 直接 pip install 隐含假设本机可上网（起草会话可 WebSearch，大概率成立）。缺口：P1-S2 前应加 `pip index versions apache-superset` 或直接依赖 P2-S0 前移。**留审查方裁量**。

### 一致性类
7. `SUP_EXPORT_AUDIT` 表在第 12 节出现但 P5-S1 只建 `SUP_USER_DEPT`——审计表属"轨道二导出治理"后续应用任务，本方案仅预留，表结构未定义。可接受但应在 P5-S1 注明"后续应用接入时建"。
8. P1-S4 配置示例 `TALISMAN_ENABLED=False` 与 P3-S4 `TALISMAN_CONFIG` 键结构未逐一与官方 config.py 对照——标注为"模板需执行时对照官方文档校正"级别的置信度。
9. 第 5 节时长估计（合计 5.5~9 天）基于"凭据确认不等机"的乐观假设；P4 人工停点 2（书面确认）现实等待期可能以天计——总览未把"人工等待"与"AI 工时"分开。**建议审查方评判是否需要拆分标注**。

### 流程类
10. 服务器 SSH 不可达处置：设为人工停点而非尝试绕行（如扫描其他端口、找跳板）——符合"不越权"原则，但用户可能期望 AI 更主动（如联系信息科的具体话术/工单模板）。方案未附沟通模板，**留审查方裁量**。
